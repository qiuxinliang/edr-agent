# EDR 证据充分性：厂商证据核验与改进计划

日期：2026-09-15。状态：研究与实施计划，未实施、未部署，不能作为验收通过记录。

## 1. 结论与优先顺序

当前应优先修复的不是“字段数量不够”，而是三件不同的事混在了一起：

1. **真实归属缺失**：不知道哪个进程实例对哪个对象做了什么。这会破坏判断，必须定位来源，不能降低要求掩盖。
2. **决策不需要的空字段**：例如不涉及文件信誉判断的行为规则缺映像哈希。应按规则说明适用性，不应自动升级成全机补证。
3. **已有事实没有被正确消费**：完整命令行已经在源证据中，但消费者可能只读摘要；同一事实被多次序列化、评分、补采。应统一事实来源，而非扩大采集。

公开证据支持“按问题组织证据、分层保留、关联分析、按需调查”；**不支持**“统一填满字段才允许告警”“所有告警都要全机取证”，也不支持“只采极少字段就能达到主流厂商效果”。

实施顺序：先验证取证资源失控修复与源归属缺口 → 建立样本和消费者基线 → 按规则区分证据充分性 → 精简 LLM 输入 → 精准补证及结果复用 → 对照验证和灰度。不要先全局放宽限制或增加采集字段。

本计划补充既有 `docs/04-client/agent/CLIENT_COLLECTION_DETECTION_PLAN_2026-09-13.md`，不替代其规则、采集投影与保留责任划分；沿用本仓库的 [Windows 采集边界](WINDOWS_COLLECTION_BOUNDARIES_2026-09-14.md)、[P0 上下文修复](P0_CONTEXT_CONTRACT_REPAIR_2026-09-14.md)、[P1/P2 流程修复](AGENT_PIPELINE_P1_P2_REPAIR_2026-09-14.md)。

## 2. 证据范围与可信度

核验范围为公开的一手材料和本地当前源码。没有访问 CrowdStrike、Microsoft、SentinelOne 的客户后台，也没有取得其完整客户原始遥测；不能提供其总体字段缺失率、每终端每日实际上传量或总体漏报率。

证据类型分别标注：

- **A：真实运营/事件披露**。厂商报告的真实事件或业务数据，不等于独立审计。
- **A-R：真实数据研究**。来源为真实告警，但结果是离线实验，不是线上 SLA。
- **B：正式产品/API/规则契约**。能证明功能或数据结构，不能证明客户总体使用率。
- **C：演示案例**。证明一种用法，不冒充真实客户事件。

研究截至上述日期；产品文档可能持续变化。所有改进目标均是本项目建议，不是厂商承诺或“行业统一标准”。

## 3. 主流厂商证据核验

### 3.1 CrowdStrike：实际事件中的筛选与关联（A）

2026-05-11 的 Automated Leads 文章披露：一次持续两小时的攻击窗口内，约 5,000 个进程创建中，75 个被标记为异常进程。75/5,000≈1.5% 是调查线索比例，不是恶意进程比例，也不是仅保留 1.5% 遥测。调查仍关联 ProcessRollup2 获取命令行与祖先进程。

启示：减少进入人工/LLM 队列的重复线索，同时保留可回查的实体事实；不能据此丢弃其余 98.5% 的原始证据。[官方案例与操作查询](https://www.crowdstrike.com/en-us/blog/ai-threat-detection-with-automated-leads/)

### 3.2 CrowdStrike：真实 Windows 告警的 LLM 研究（A-R）

原论文使用 SOC 人工标注的 Windows 告警，训练/验证/测试分别为 **388,336 / 59,162 / 42,686 条**，按连续 **8 / 2 / 1 周**划分。输入包含进程链、命令行、路径、普遍度和检测上下文，明确允许字段缺失。

必须注意指标口径：博客用“98%/99% 精确率档位”概括结果；原论文表 1 的推理加校准系统，良性类高置信档精确率从验证集 **98.0%** 降到测试集 **90.8%**，测试召回率为 **64.8%**；恶意类测试精确率/召回率为 **98.9% / 53.0%**。不能把验证阈值当成测试保证，更不能移植为我们的自动处置阈值。[原论文，第 3–5 页与表 1](https://arxiv.org/pdf/2607.28460)、[厂商博客，2026-08-17](https://www.crowdstrike.com/en-us/blog/teaching-ai-to-reason-through-detection-triage/)

这支持按实际判别效果验收，而非按空字段数验收。它不证明某组固定少量字段对全部攻击充分，也不证明减少采集本身提高准确率。

### 3.3 CrowdStrike：客户勒索攻击调查（A）

2021 年公开客户案例由异常 bitsadmin 下载切入，结合进程树、命令行、远程执行痕迹、用户和登录来源追踪攻击路径。公开查询围绕具体线索进行进程关联，而非先收集每个对象的所有属性。[Falcon Complete 客户事件复盘](https://www.crowdstrike.com/en-us/blog/how-falcon-complete-stopped-a-big-game-hunting-ransomware-attack/)

该案例是调查方法证据；年代较早，没有公开总体缺失率，也不是现代 LLM 分类效果实验。

### 3.4 CrowdStrike：正式业务架构披露（B）

FY2026 10-K 描述本地分析与向平台传输选定高保真数据的分工。这支持区分本地检测和云端处理，而不是把所有本地观测直接塞进模型。[SEC 原始披露](https://www.sec.gov/Archives/edgar/data/1535527/000153552726000010/crwd-20260131.htm)

这是厂商架构陈述，不是每台终端实际数据量；“本地未过滤观测”也不能解释为操作系统每一种事件均被观察。

### 3.5 Microsoft：真实 SharePoint 攻击的多类证据（A）

2025-07-22 披露的 SharePoint 攻击活动包含多条调查路径：用进程与父进程命令行发现可疑执行，用文件事件发现落地对象，用网络/DNS 线索关联通信；另有按已知哈希检索的分支。[Microsoft 实际攻击调查与 hunting queries](https://www.microsoft.com/en-us/security/blog/2025/07/22/disrupting-active-exploitation-of-on-premises-sharepoint-vulnerabilities/)

启示：行为分支与 IOC 分支需要不同证据。没有哈希不意味着无法判断异常执行；但判定“命中某个文件哈希 IOC”必须有对应对象的可信哈希。公开 hunting query 也不等于产品全部实时检测实现。

### 3.6 Microsoft：实际产品字段契约（B）

DeviceProcessEvents 文档明确说 SHA256 字段通常不填充，并建议在该查询场景使用可用的 SHA1；同时提供进程唯一标识等关联字段。[官方表结构](https://learn.microsoft.com/en-us/defender-xdr/advanced-hunting-deviceprocessevents-table)

这直接反驳“每条进程事件必须有 SHA256 才算合格”的普遍要求；不构成降低证据完整性校验算法的理由。查询标识用途与安全完整性哈希用途不同，也不能据此删除文件信誉/IOC 规则所需哈希。

### 3.7 Microsoft：调查包是独立且有去重约束的动作（B）

收集调查包需要专门权限和请求原因；设备已在采集时返回错误，而非叠加启动。成功提交返回 MachineAction，不能当作采集完成。[Collect investigation package API](https://learn.microsoft.com/en-us/defender-endpoint/api/collect-investigation-package)

响应文档另列调查包的采集内容及采集状态报告。[终端响应与调查包](https://learn.microsoft.com/en-us/defender-endpoint/respond-machine-alerts)

启示：有权限、有理由、有执行状态的按需取证，与常驻遥测不是一回事。本项目可以进一步复用进行中的任务；这是我们的设计选择，不是该 API 已实现共享等待的声明。

### 3.8 Elastic：明确不承诺全量系统事件（B）

Elastic Defend 文档说明，为平衡检测、存储和性能，事件可能聚合、截断或去重，不提供所有系统事件的完整记录；需要额外可见性时，按事件类别使用补充集成。[官方事件采集边界](https://www.elastic.co/docs/solutions/security/manage-elastic-defend/event-capture-elastic-defend)

因此“主流 EDR 必须上传所有读操作、所有字段”不成立。但其产品取舍不能证明我们任意位置的静默截断安全；我们的检测消费者和证据保留约定仍须逐项验证。

### 3.9 Elastic：检测条件与后续调查分开（B）

“Execution from Unusual Directory - Command Line”规则使用进程类型、名称、参数和部分父进程条件；调查指南另外建议检查普遍度、签名、网络活动、文件哈希等。[实际发布规则及调查指南](https://www.elastic.co/docs/reference/security/prebuilt-rules/rules/windows/execution_from_unusual_path_cmdline)

这是“触发线索所需”与“调查定性所需”分层的具体例子；不能把规则命中直接等同于恶意，也不能把指南里的每个建议都变成每条事件的硬性必填项。

### 3.10 SentinelOne：实体关联与案例边界（B/C）

Deep Visibility 的公开说明以 Storyline/TrueContext 标识关联相关活动。[官方关联查询说明](https://www.sentinelone.com/blog/rapid-threat-hunting-with-deep-visibility-feature-spotlight/)

另一篇 CWPP 文章演示了命令注入后关联 shell、Python 和工作负载上下文；文章明确是说明性案例，不应当作真实 Windows 客户样本。[官方演示](https://www.sentinelone.com/blog/decrypting-sentinelone-detection-the-behavioral-ai-engine-in-real-time-cwpp/)

可借鉴共享实体和关联视图；本次没有取得其客户原始数据、字段缺失比例或 LLM 消融实验，不做数字对标。

### 3.11 对原建议的核验结论

| 原判断 | 结论 | 必须保留的限制 |
|---|---|---|
| LLM 不需要接收每条原始事件、每个重复字段 | 有证据支持分层与筛选；具体最小集合仍待实验 | 减少输入不等于删除本地事实 |
| 缺哈希或祖父信息就必然不可判断 | 不成立，取决于规则与待回答问题 | 哈希 IOC、身份关系类判断不能缺其必要证据 |
| 缺信息就应自动收全机调查包 | 没有找到这种普遍必要性的证据 | 某些调查确实需要授权的深度取证 |
| 所有大小限制和门禁都应取消 | 不成立 | 容量、并发、期限、身份与权限边界必须存在 |
| 当前只需改评分，采集已经充分 | 不成立 | 实测仍有文件对象与进程代际不能绑定的记录 |
| 可用厂商阈值直接证明我们的自动化安全 | 不成立 | 数据分布、模型、规则与处置成本均不同 |

## 6. 目标链路：少传重复事实，不丢关键关系

```text
OS 事件/正式接口
  → 解码与来源标注
  → 操作主体实例 + 目标对象 + 时间/动作绑定
  → 现有本地事实/引用与耐久队列
       ├→ 本地规则判断
       ├→ 按用途保留/上传 → 服务端类型化证据 → 精简 LLM 包
       └→ 具体缺口查询 ← 缓存命中 / 授权定向采集
                                              ↓
                                   证据引用 + 判断/未知 + 处置资格
```

四种责任分开：**观察什么、保留什么、上传什么、给 LLM 看什么**。实现仍由现有模块承担，不新增四个服务。

### 6.1 共用证据骨架

规则证据至少能够回答其适用的问题：

- 哪台终端、哪个进程实例/用户主体；用租户、端点、启动实例与代际边界关联，不靠 PID 单值。
- 什么时间、对什么对象、执行什么操作，结果是成功、失败还是未知。
- 为什么命中：规则版本、实际谓词/命中片段、必要事件序列及来源引用。
- 哪些关系是直接观察，哪些是推断，哪些证据缺失、不可恢复或相互冲突。

不是要求所有事件序列化全部这些字段；可通过权威事实引用物化。无进程语义的事件不强制套进程链。时间接近只能形成待核查关联，不能伪装为因果关系。

### 6.2 按检测问题定义证据，不做全局满分表

下表是设计起点；实施时逐条映射现有规则谓词，不宣称这些字段可单独完成全部攻击定性。

| 规则/调查问题 | 应优先保证的证据 | 仅在相关问题上补充 | 缺失时的正确行为 |
|---|---|---|---|
| 可疑命令执行 / LOLBin | 主体实例、执行路径与实际命令语义、命中条件；规则涉及启动链时保留父链 | 文件信誉、祖父信息、脚本内容、资产用途 | 可以保留线索；命令尾部丢失导致谓词不确定则不能宣称命中已证实 |
| 凭据文件访问 | 操作者代际、可信目标对象/路径、操作类别、时间；权限和结果按谓词需要 | 用户安全上下文、后续外传、文件内容摘要 | 目标对象无法绑定时不可判为已访问该凭据文件，不能用同目录文件代替 |
| 横向移动 | 源/目标实体、账号/登录或远程执行关系、时间与执行证据 | 登录类型、会话关联、目标进程链、管理任务记录 | 仅发现远程管理工具不能等同横向攻击 |
| 可疑外传 | 进程关联、目标地址/域名、实际流量/连接事实及时间；数据量按谓词需要 | DNS、协议、关联文件/数据敏感性 | “已连接”不能写成“已外传”；无网络样本不能验收该能力 |
| 批量破坏/勒索行为 | 同主体对对象的变更序列、覆盖窗口、可信数量语义与结果 | 诱饵命中、扩展名/内容变化、备份动作、授权软件基线 | 聚合计数不可靠时明确至少 K 或未知，不能冒充精确计数 |
| 哈希 IOC / 映像信誉 | 对应文件对象的哈希算法、值、来源时点与绑定质量 | 签名、普遍度、行为链 | 事后路径快照可作调查线索，不能伪装执行映像哈希 |
| 脚本内容判定 | 对应脚本内容或可验证的等价事件、调用主体和来源绑定 | 脚本签名、下载来源、静态信誉 | 涉及内容判定才需要内容；仅看到脚本路径不自动要求全部脚本属性 |

### 6.3 缺失状态与判断资格

复用现有 status/reason/quality，仅补充确有消费者的语义：可用、不适用、未采集/不支持、未保留、暂未到达、采集失败、来源冲突。事后可查询与不可恢复另行说明，避免一次新增十几套状态机。

分别输出：

1. **遥测质量**：字段覆盖与源健康，不直接驱动处置。
2. **问题充分性**：这个规则/调查问题是否有足够证据；可记录替代证据与尚未解决的问题。
3. **处置资格**：目标身份、授权、时效、策略、签名和风险要求是否满足。

未知不是良性；可以带缺口保留告警，也可以仅因处置依据不足而拒绝自动隔离。不能让一个 13 项比例同时控制这三件事。

## 7. 具体改进包

### A. 先修归属与消费，不先扩大采集

- 对文件读两类缺口分别抽样，保存 source event → 解码 → 对象绑定 → 进程代际 → 本地候选 → 上传记录 → 告警引用的配对结果。
- 区分规则投影确认不相关而跳过昂贵增强，与本应增强但失败；两者计数、验收分母不能合并。
- 无法事后恢复的事实必须在事件时保留适当标识；不能以“以后按需采”替代短生命周期主体、临时文件或瞬时脚本证据。
- 逐个检查页面/API/LLM/自动化消费者使用的是 preview 还是 source_evidence；不再因摘要变短要求 Agent 重采已存在原文。
- 只有证明现有正式接口无法提供必要事实，才单独评估新传感器/驱动；继续遵守既有 Windows 能力边界文档。

### B. 将“通用完整率”降为诊断信息

- 保留 context_completeness 的旧协议语义，先核对消费者；页面明确显示“遥测字段覆盖”，不再以“总体证据完整度”误导。
- 决策在现有规则权威定义处声明必要证据、适用条件、允许的替代来源；服务端和客户端不得维护相互矛盾的第二套规则。
- 第一批覆盖实际样本对应的 CRED、DISC、EXEC、LMOVE、注册表查询规则；不得仅按规则名字套模板，需核对每条实际谓词。
- 缺少非关键字段不触发补证；关键缺口先判断补证是否能解决，不能只把列表清零当成成功。
- 旧消费者迁移完成后，才删除已无支持对象的重复判断/兼容辅助函数；不直接移除质量诊断。

### C. 合并 LLM 中的重复事实

- 在现有分析包构造器中，按实体和证据引用组织：命中原因、关键事件序列、主体链、相关目标、反证、缺口。
- 同一命令行/进程事实只保留一个权威值；时间线和图摘要引用它。来源不同且冲突的值不能当重复删除。
- 完整事实留在源证据；超出输入预算时选取语义完整片段并提供可检索引用，禁止隐式切掉参数、破坏 JSON 或 UTF-8。
- 有时省略一段无关命令安全，有时尾部就是恶意参数；需按命中跨度与上下文实验，不设新的“固定 X 字符足够”结论。
- 模型输出采用结论、证据引用、反证/不确定性和待核查问题，不要求冗长解释，更不把解释长度当证据质量。
- 终端命令行和脚本是非可信输入；其中“忽略前文”等文字不能取得工具权限。送外部模型前执行既有租户授权和秘密脱敏，不因取证需求外发整机敏感数据。

### D. 精准补证与复用现有执行链

补证请求必须能表达：**为回答哪个问题、哪个实体实例、哪个时间窗、缺什么事实、可接受何种来源、已有何种证据、什么时候终止**。先用现有命令参数/回执承载；有实际消费需求才扩展协议。

执行顺序：已有服务端证据 → 本地证据缓存 → 定向读取/查询 → 必要且已授权的调查包。不能因为“需要更多上下文”直接走最后一级。

- 去重键覆盖租户、端点、主体/对象代际、证据类别、时间窗和影响语义的策略版本；不能只按 PID 或告警 ID 去重。
- 同需求已有任务时关联已有任务，完成后复用合格结果；不同主体、不同文件版本、不同证据问题不能误用旧结果。
- 保留当前端点串行保护、10 分钟自动快照预算、耐久 outbox、签名、过期和回执检查。语义去重是补充，不是取消资源安全网。
- 预算受限应保留待解决问题和原因，不能伪报补证成功，也不能每次 LLM 重试都再发相同命令。
- 已知不存在/已过期/无法恢复的证据，结束本次需求并明确不确定性；有限任务有期限、取消和终态，不永久循环采集。
- 本产品自己的采集活动保留可追踪来源，用于抑制重复补证；不能整体白名单化其所有进程后忽略真实滥用。

### E. 限制分类，而非全面取消

| 限制类别 | 处理原则 | 验收方式 |
|---|---|---|
| 固定显示摘要长度 | 可以保留，但不可成为检测/LLM 唯一证据 | 长命令行与尾部命中案例，预览明确标识 |
| 所有规则统一字段门槛 | 改为规则适用性与问题充分性 | 同字段缺失在不同规则有正确不同结果 |
| 同事实多路径重复计算/补采 | 合并、缓存或结果复用 | 并发请求仅一次实际采集，所有调用者可追踪结果 |
| 关键上下文任意次数限额 | 已有 capacity_bound 修复先验收，不再另造固定计数门槛 | 关键关系保留；磁盘满/事务失败明确可见 |
| 文件数、字节数、磁盘容量、并发、超时 | 保留，阈值通过工作负载测量调整 | 上限触发有清单/原因，停止可恢复，无递归归档 |
| 身份代际、证据绑定、命令授权、信任验证 | 保留 | 冲突/过期/伪造不能得到有效证据或自动处置 |

64 MiB/64 文件只是当前基线，不声称足够所有深度调查。超出基线若确有需要，应成为明确授权、独立预算的调查任务，不隐式扩张自动 quick 范围。

## 8. 验证设计：证明精简没有掩盖问题

### 8.1 数据集与基线

1. 定位历史 220 条原始集合；记录清单摘要、版本、规则、时间、来源引用、是否重复及标签来源。未定位则明确缺口。
2. 纳入现有 98 条历史告警，但以事件链/测试活动分组；相同攻击产生多条告警不能当成独立样本扩张统计置信度。
3. 加入真实良性样本：合法管理、安装更新、备份、开发脚本以及 Agent 自身取证，避免只测恶意触发。
4. 由可核查测试步骤和人工复核给出标签；区分“规则命中成立”“行为恶意”“应自动处置”。LLM 原有答案不能当真值。
5. 按时间和事件链分割调优集、验证集、冻结测试集；同一链不能泄漏到两侧。版本变化另留新样本验证漂移。
6. 数据、规则、模型、提示词、分析包版本和引用哈希可追溯；只提交脱敏固定回归夹具，不提交生产原始证据。

### 8.2 四组只读回放

| 组 | 输入 | 要回答的问题 |
|---|---|---|
| A 当前基线 | 现有分析包 | 当前准确性、未知率、重复量和成本是多少？ |
| B 精简包 | 按规则必要证据 + 已有相关事实，不主动补证 | 哪些冗余可去掉，哪些省略会改变判断？ |
| C 精简加定向补证 | B + 只读查已有缓存/已存在调查结果 | 有目的补证是否修复 B 的具体错误？ |
| D 全部已取得证据 | 在预算内提供已取得的完整相关证据 | 缺少信息与模型/规则能力不足能否区分？ |

回放不向终端下发命令、不触发自动隔离、不制造“完整证据”。D 不是重新采集整机，也不天然是真值。若 D 仍不确定，不能默认继续增加采集。

逐类消融：哈希/签名、祖父链、用户名/权限、文件来源、网络关联、重复表示；一次改变一个因素。另做事件聚合消融，不能把删字段和删事件混在一次实验中。

### 8.3 指标与建议目标

先记录基线，再锁定性能目标；以下减量目标是初始实验目标，不是新增发布硬门禁。

| 维度 | 度量 | 验收原则 |
|---|---|---|
| 判断质量 | 按规则族的精确率、召回率、未知率、混淆矩阵、置信区间 | 所有已知关键攻击夹具不得新增漏检；统计样本不足时不能宣称总体等效 |
| 拒答/未知 | 未知数 / 全部样本数及其原因 | 不允许把全部困难案例变为未知后只报告已回答样本的准确率 |
| 处置安全 | 错对象处置、错误隔离、恶意告警错误自动关闭 | 固定身份/授权回归必须全部通过；影子阶段不执行自动处置 |
| 源质量 | 应适用字段中的可靠归属率、不可恢复缺口、冲突数 | 不将 N/A 纳入失败分母；也不能将错误标成 N/A 提高比例 |
| 端到端保真 | 对应事件/代际的哈希、引用、谓词和语义一致性 | 同一个事实逐层对照，不能只比记录条数 |
| LLM 成本 | 每案输入 token、重复事实比例、P50/P95 时延 | 初始争取输入 token 中位数降低 30%；质量优先，不达目标不靠丢证据凑数 |
| 补证成本 | 每端点每小时实际任务数/字节、命中缓存比例、失败/取消比例 | 相同有效需求并发夹具只启动一次；真实重复任务初始争取降低 80%，须有可比基线 |
| 资源 | CPU、RSS、磁盘增长、上传量、队列年龄、压力下丢弃原因 | 相同负载比较，阈值由当前支持矩阵和资源预算决定 |

自动处置和自动关闭分别定风险阈值；不能用“整体准确率”掩盖少数严重错误。若样本规模不能支持阈值置信度，继续人工复核而非宣布上线。

### 8.4 UTM 三类受控案例

在取证膨胀修复的部署身份与资源边界验证通过后，另行执行获授权的低风险案例；本计划不执行它们。

- **命令语义**：良性标记命令包含超过预览长度的关键尾部，验证源、告警、页面、LLM 的一致性；不得仅检查显示长度。
- **文件归属**：临时测试目录中创建/读取/写入，包含并发和进程退出，逐条核对主体代际与对象；不读取真实凭据或敏感文件。
- **网络关联**：回环或明确授权目标，核对连接主体、目的与结果；不得将连接成功解释为外传成功。

每类保留操作真值、版本、时间窗、事件引用、预期/实际差异。UTM ARM64 仅证明该环境；Windows Server/AMD64 的采集与运行时仍需对应原生验证。PowerShell 行为及 MSVC 编译问题不能由 macOS 静态测试代替。

## 9. 分阶段实施与交付

工期为依赖就绪后的粗估，约 10–15 个工作日；不是已承诺完成时间。可并行只读分析，涉及同一所有者的修改串行合入。

| 阶段 | 责任模块 | 交付物与退出条件 | 估计 |
|---|---|---|---|
| 0 安全基线 | Agent/取证、发布 | 验证已有归档修复在目标版本生效；资源有界；完成文件读两类缺口的单事件链定位。阻断项未解决不跑会放大的自动取证 | 1–2 日 |
| 1 判据与样本 | 规则/服务端/测试 | 找到或明确未取得 220 条；冻结可用样本；完成消费者清单及各规则必要/可选/N/A 证据映射 | 2 日 |
| 2 充分性与输入 | 服务端/前端 | 保留旧评分兼容，增加规则适用性；统一精确事实消费与预览标识；完成 A/B/D 回放 | 2–3 日 |
| 3 补证收敛 | 服务端任务/Agent 定向读取 | 先查缓存、再定向补证；复用进行中/已完成结果，保留预算与回执；完成 C 组及重启/并发验证 | 3–4 日 |
| 4 实机与灰度 | 验证/运维 | UTM 三类案例，支持矩阵原生回归；影子比较、新时间窗人工复核，明确是否达标 | 2–4 日 |

三条工作线即可，不新增长期服务：规则/评分及消费者；Agent 归属与证据保留；回放/并发/发布验证。协调者负责契约一致性与最终证据审阅，避免多人分别改同一个“完整率”定义。本轮没有新启动子任务。

### 9.1 回归归属与最小变更

- 规则/评分：扩展现有 `p0_context_test.go`、`p0_command_semantics_test.go`，覆盖 N/A、替代证据、关键缺口、冲突来源与长命令。
- LLM：在现有分析包及 source_evidence 测试中验证事实引用、预算、中文/转义、末尾参数与脱敏；不新增只匹配代码字符串的脆弱门禁。
- 并发：扩展现有 `trust_gate_evidence_budget_test.go` 等行为验证；同端点并发、不同租户、不同代际、超时、重启和既有结果过期必须覆盖。
- Agent：复用文件读绑定、`test_file_object_binding.c`、`test_local_evidence_cache_candidate.c`、`test_p0_direct_emit_suppression.c` 的行为测试；只对实际改动扩大原生回归。
- 发布：若仅改服务端/UI，不重复发布 Agent；涉及采集或共享协议时再触发相应 Windows AMD64/ARM64 构建、实际产物和生命周期验证。
- 不删除失败测试换通过；不为文案/文档变化运行整套原生编译。新测试验证结果和安全边界，而非硬编码实现路径或词句。

### 9.2 兼容、发布与回滚

- 先让消费者识别精确证据与预览，再修改生产者；旧版本仍明确能力不足，不能伪报新语义。
- 影子阶段只计算新结果，不改变隔离/关闭/补证行为；记录分歧供复核。
- 小范围验证后再按现有发布机制扩大。若引入临时影子开关，必须指定所有者和移除条件，不留下永久双轨逻辑。
- 回滚恢复旧策略/读取路径，但不删除新保留事实和审计；新增协议字段需向后兼容。任务取消/失败仍有耐久回执，不能因回滚丢掉正在执行的任务。
- 每个实施包完成必要验证后独立提交；记录部署版本与测试报告，不用“编译成功”替代实际效果验收。

## 10. 最终保留项、验收清单与风险

**keep:** 进程代际和文件对象绑定；证据来源/完整性；TLS、签名、授权和反重放；离线队列、引用一致性、回执及恢复；资源预算、超时和终态；安装/升级/卸载安全；源端明确不可评估的诊断。

实施验收清单：

- [ ] 历史数据清单可追溯，220 条是否实际取得明确标注。
- [ ] 文件路径、进程身份真实缺口与不适用/主动投影分别定位。
- [ ] 固定完整率不再替代规则充分性与处置资格。
- [ ] 摘要、精确源及各消费者语义一致，长命令关键尾部可用。
- [ ] A/B/C/D 使用同一冻结样本、模型和规则版本，报告未知和错误而非只报成功案例。
- [ ] 相同补证需求复用，容量/并发/过期/回执与恢复边界保留。
