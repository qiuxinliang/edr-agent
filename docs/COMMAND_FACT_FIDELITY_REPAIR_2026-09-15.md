# 命令行事实保真修复与反复失败原因复盘

日期：2026-09-15。基线：`f0fcabcf`，运行实测基线为 3.2.501。
范围：已确认的命令行预览覆盖/阻塞完整事实问题，以及这条路径的来源传播。
状态：源码修复与本地回归完成；尚未作为新签名版本在 UTM 验收，不代表整体上下文问题解决。

## 1. 已确认的事实与根因

[3.2.501 实机报告](AGENT_3_2_501_VALIDATION_2026-09-15.md) 记录：同一进程代际，
ProcessCreate/create/write 命令行长度为 1308，两条 FileRead 为 1023，且没有截断标记。
两条读取的代际均正确。因此“进程没有关联”已不是这一轮命令行短缺的解释。
实机报告中的长度是查询得到的文本长度；以下合成回归明确按 UTF-8 字节计数，不混用单位。

源码证据链：

1. `collector_win.c::edr_collector_pid_cache_update` 将命令行放进 1024 字节缓存，原来直接截断且不记录来源损失。
2. `edr_collector_pid_cache_enrich` 将前缀放进空字段，FileRead/registry writeback 原来只写 `cmd`，未携带字段来源。
3. `behavior_from_slot.c` 原来不解析 `command_line_origin`，即使上游写入该键，也不能传到后续消费者。
4. `process_cached_generation.h` 原来只给空命令行补历史事实；已有的短值阻塞了完整缓存。
5. 同类检查确认 `preprocess_pipeline.c::p0_bind_process_generation` 的成功 live-query 分支也只补空字段。
   只修历史保留分支，会留下另一条有相同缺陷的处理路径。

这不是必须继续采集更多数据才能解决的问题，而是**短预览、完整事实与来源状态没有一起流转**。

## 2. 本次实现

- 保留热路径预览的 1024 字节容量，不增加缓存层、后台任务、采集种类、数据库表或配置开关。
- 将预览显式命名为 `EdrProcessCommandPreview`，携带截断状态；UTF-8 边界不保留半个字符。
- FileRead/registry 共用命令行和来源写回逻辑。先写来源/截断元数据，再写命令；空间不足不写出无标记的截断命令。
- 抽出原 ETW1 文本写入实现到内部头文件，使实际生产写入边界可以参与跨平台行为测试，而非重写测试模型。
- 补齐 `command_line_origin` 的解析与过长值诊断。
- 历史缓存和 live-query 共用事实采纳规则：先验证代际，再要求已知预览、相符前缀、无长度降级。
  普通非空直接观测、不明来源和冲突内容不按“谁更长”盲目覆盖。
- 有完整历史事实时优先复用；否则只在原本已验证的同一 live handle 上查询。
  失败保留已有前缀及截断状态，不能清空证据或借用复用 PID 的新进程。
- 只有被完整事实替换的 `source.cmdline` 标记被清除；其他字段损失、`source.list_overflow`、
  `NOT_EVALUABLE` 均保留。合并后不宣称所有字段 `COMPLETE`。
- 保持现有 StartKey/creation/event-time 校验、网络归属边界、TLS、命令签名、耐久队列、自动隔离策略不变。

采用简化审查方法的实质影响：合并 FileRead/registry 写回以及历史/live 事实采纳规则；
没有通过再增大字符串、再加一份事实缓存或取消安全门禁来修复。

## 4. 为什么问题持续多轮

1. **分层数据契约缺失。** 多份缓存都叫命令行，但有的只是预览，有的是进程事实；后续使用“非空”代替“来源可信且足够完整”。
   后端再给整体完整度评分，不能恢复已丢失的来源语义。
2. **修复与测试停留在局部。** 上一轮修好了代际绑定，也验证了空字段补全，却未把真实的非空短值作为回归输入。
   同类问题还存在于 live 分支。之前没有覆盖这个组合路径，是工程验证不足，不能归因于用户部署方式。
3. **发布成功与运行生效混淆。** [Worker 实证](EVIDENCE_BUDGET_RUNTIME_VERIFICATION_2026-09-15.md)
   显示更新过 API，但实际执行补证的 Worker 仍为旧进程；更新正确 owner 后命令才收敛。
4. **版本判断曾使用了错误证据。** 3.2.500 的发布时间晚于 3.2.501，导致只看 `/releases/latest` 得出错误的可用版本结论。
   之前的判断已在 3.2.501 报告纠正，后续以指定 tag、commit、产物 SHA 和实际运行进程为准。
5. **“缺少上下文”包含不同问题。** 真实对象/身份缺失、已采事实未消费、规则不需要的空字段、本地保留未上送、
   Worker 重复补证不能用一个空字段比例解释。若不分别定责，就会每修一层暴露下一层，然后误判为同一个问题一直没修好。

## 6. 3.2.502 Windows 测试失败：截断标记常量先被编译器截断

### 原始证据与边界

- 失败版本：`win_3.2.502`，commit `2785d7a35d2082381a48a785e6c35d89516ea384`。
- [运行 34971566723](https://github.com/qiuxinliang/edr-agent/actions/runs/34971566723) 中，
  [amd64](https://github.com/qiuxinliang/edr-agent/actions/runs/34971566723/job/104388882225)
  与 [arm64](https://github.com/qiuxinliang/edr-agent/actions/runs/34971566723/job/104388882208)
  均在 `test_local_evidence_cache_candidate.c:4537` 的
  `edr_behavior_source_field_truncated(decoded, "source.command_line_origin")` 断言失败。
  这是测试执行失败，不是链接失败，也不是此前同名测试中的进程树断言。
- 两个架构的 MSVC 19.44 编译日志均已在 `behavior_from_slot.c:1350–1351`
  报 `C4309: truncation of constant value`，在 DNS 位传参处报 `C4245`。
  这些警告没有终止编译；不能把最后的 CTest 包装异常当作原因。

### 已定位机制与同类边界

`truncation_mask` 虽然是 `uint64_t`，定义标记的普通 C `enum` 却先经过 MSVC 的
32 位表示。`1ull` 只约束移位表达式，不能保证枚举成员保留该类型。
[Microsoft 的 C 枚举说明](https://learn.microsoft.com/en-us/cpp/c-language/c-enumeration-declarations)
也规定了枚举常量的 `int` 约束。

用实际修改前后定义，分别在 Clang 的 `x86_64-pc-windows-msvc` 与
`aarch64-pc-windows-msvc` 目标生成常量返回值，两个目标结果一致：

| 标记 | 原定义转为 uint64_t | 修正后 |
| --- | --- | --- |
| DNS，第 31 位 | `0xffffffff80000000`，符号扩展 | `0x0000000080000000` |
| 截断列表溢出，第 32 位 | `0` | `0x0000000100000000` |
| 命令行来源，第 33 位 | `0` | `0x0000000200000000` |

因此过长来源被解析器清空后，`truncation_mask |= 0` 没有保留原因，最终触发断言。
新增第 33 位暴露了既有第 32 位的同类缺陷；只改单个新标记会留下隐患。
此前 macOS 与 MinGW 检查允许更宽的枚举值，不能替代 MSVC 语义验证。
这也解释了为什么本地通过，而 Windows 两架构均失败；无需再增加命令行容量。

### 修正与验证范围

- 同一组 34 个标记改为显式 `UINT64_C(1)` 位掩码常量；不改变结构体、缓存容量或线协议。
- 对第 31–33 位保留编译期数值不变量，避免再次在生成产物前悄悄丢位。
- 原第 4537 行断言保留。现有解析测试补 9 个场景：DNS/来源刚好容纳、到达与超过容量，
  截断列表超长，以及 DNS 与来源同时截断；要求标记互不混淆，后续 `COMPLETE` 不抹掉损失。
- 定向 CTest：`local_evidence_cache_candidate`、`cmd_actor_and_script_artifact`、
  `detection_sensor_bridge`，3/3 通过；使用真实解析代码，本地证据测试仍含原非生产 P0 IR stub。
- 实际定义的双目标编译对照：修改前各 31/34 个数值正确，修改后各 34/34 正确。
- MinGW x64 语法检查及 Clang C11 严格枚举约束检查通过；`git diff --check` 通过。

以上证明本次常量窄化机制及本地候选修正，不是修改后 MSVC 原生运行的替代证据。
尚未推送、触发新发布、部署或改动 UTM；原生 amd64/arm64 的现有 54 项发布测试仍待新候选运行。
